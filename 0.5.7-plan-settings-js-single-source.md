# settings.js: single source of truth for app settings + state

## Context

The `max period` slider says 4..4000 in the UI but a load-from-save clamps to 20000 because the slider's max and the loader's clamp drifted out of sync. Root cause is duplication, not a typo — the same pattern (slider bounds, default, loader clamp, runtime clamp) repeats 4-5 times for `maxPeriod`, again for `samplesPerTurn`, and again for `trailCap`. The app state bag (`app` field in saved JSON) is in the same shape: split across `gear.js` (default, loader whitelist) and `main.js` (live `App` initializer, snapshot, apply, storage key). Adding a new persisted toggle today means edits in 4 places.

User intent: "all setting and constants and state - good to store in one place to easy get and easy decide do we need save/load them or only use as constants". Centralize duplicated constants + the persisted state schema, and make "persisted vs runtime-only" a visible per-field decision.

## Goal

A new `js/settings.js` that owns:

- every slider bound (min, max, step), default, and a `clamp(field, v)` helper used by both the runtime setters and the save loader.
- the on-disk `app` schema: per-field default, type, getter from live `App`, apply recipe into live `App + GUI`, and a `persist: true|false` flag.
- `STORE_KEY` for autosave.
- pure helpers: `defaultApp()`, `sanitizeApp(s)`, `snapshotApp(App)`, `applyApp(s, App, GUI)`.

After this lands: changing `maxPeriod` from 4..4000 to anything else is one edit in `js/settings.js`. Adding a new persisted toggle is one entry in `APP_SCHEMA`. Loading a legacy save with `periodThreshold` still works.

## Non-goals

- No change to the on-disk save format. The `app` field schema and the legacy `periodThreshold` alias are preserved.
- No change to GUI layout, slider types, HTML, CSS.
- No build step, no modules, no ES6 imports. Classic `<script>`.
- Not touching single-file constants that aren't duplicated: `MAX_GEARS`, `MIN_GEAR_R`, `MAX_LEVEL_N`, `WHOLE_POINT_BUDGET/SLICE_MS/CHUNK`, `GESTURE_SEG_BUDGET`, `GESTURE_FRAME_SLICE_MS`, `TAP_PX`, `EPS`, `TAU`, `R.MAXSEG`, `R.GLOW_CAP`, `R.MAXVERT`, `MIN_RING`, `MAX_TURNS`, `WHOLE_CHUNK`. They each appear in one file; moving them is churn.
- `Gear.CAP` (40000) and `DEF_TRAIL` (20000) stay in `gear.js` (they describe the ring buffer, not user settings). `Settings.LIMITS.trailCap.max` is set to 40000 with a comment "must equal `Gear.CAP`".
- `colorMode` is a top-level scene field, not in `app`. Stays as-is.
- No in-app config screen or `default.js`-based settings UI.

## Design

### `js/settings.js` (new)

Classic IIFE. Exposes `root.Settings` (and `module.exports` for node). Loaded first in `index.html` so the constants exist before `gear.js` reads them in `defaultAppState` / `deserialize`.

Structure:

- `LIMITS` table: `{ maxPeriod: {min, max, step, def}, samplesPerTurn: {...}, trailCap: {...with floor} }`.
- `clamp(field, v)`: pure helper. Returns `Math.max(L.min, Math.min(L.max, Math.round(v || 0)))`, with optional `L.floor`.
- `APP_SCHEMA` array: one entry per persisted field, each `{ key, type, def, persist, alwaysApply?, get(App), apply(s, App, GUI) }`. The `apply` signature is `(s, App, GUI) -> void`; recipes are explicit per-field closures that mirror `applyAppState` in `main.js:778-825` field by field.
- `defaultApp()`: iterates schema, returns `{ key: def }`.
- `sanitizeApp(s)`: input may be missing, null, or partial. Coerces bools to defaults, clamps `maxPeriod` / `samplesPerTurn` via `clamp`, maps legacy `periodThreshold` → `maxPeriod`, normalizes `mode` to `'animate'|'whole'`, falls back to `defaultApp()` if input is unusable.
- `snapshotApp(App)`: iterates `persist:true` entries, calls `f.get(App)`, returns the bag.
- `applyApp(s, App, GUI)`: calls `sanitizeApp(s)`, then for each schema entry skips if `s[f.key]` is `undefined` or already equals `f.get(App)` (unless `alwaysApply:true`). `mode` is `alwaysApply:true` because the current code calls `GUI.setMode + GUI.setColorMode` even when `s.mode === App.mode`.

**Recipe fidelity rules** (the highest-risk item — see checklist below):

- `maxPeriod` / `samplesPerTurn`: write `App.<field> = s.<field>` directly, call `GUI.setMaxPeriod` / `GUI.setSamplesPerTurn`. Do **not** call `App.setMaxPeriod` — that would trigger a redundant `recomputeWhole`. The original code writes the field and lets `loadObject` / `afterSceneChange` handle the recompute.
- `overlay`: set `App.overlay.on`; if becoming on, call `App.invalidateOverlay`; call `GUI.setOverlay`; call `markDirty()`.
- `showCircles`, `showDial`, `showPoints`, `glowPoints`, `drawTrails`: set the field, call the `GUI.setXxx`, call `markDirty()`.
- `paused`, `symmetry`: set the field, call the `GUI.setXxx`. No `markDirty`.
- `mode`: `alwaysApply:true`. If `s.mode !== App.mode` call `App.setMode(s.mode)`. Otherwise call `GUI.setMode(App.mode); GUI.setColorMode(App.colorMode);` (matches current same-mode branch).

## Risks and their resolution

- **Test loader order.** `test/run.js` does `require('../js/gear.js')` synchronously. If `gear.js` reads `Settings` at module-init, it throws. Resolution: `defaultAppState` reads `Settings.defaultApp` only inside its function body; `test/run.js` requires `settings.js` first; `stub-dom.js` loads `settings.js` first into the sandbox.
- **Apply recipe side-effect matching is the highest-risk item.** The recipes must mirror the current `applyAppState` field by field. The checklist above is the contract. The two non-obvious gotchas:
  - `maxPeriod` / `samplesPerTurn` recipes must write the field directly and call `GUI.setMaxPeriod` — **not** `App.setMaxPeriod` (which would recompute redundantly).
  - `overlay`, `showCircles`, `showDial`, `showPoints`, `glowPoints`, `drawTrails` recipes must call `markDirty()` at the end, matching `main.js:798,809,812,815,818,823`.
  - `mode` must be `alwaysApply:true` because the same-mode branch in the original always calls `GUI.setMode + GUI.setColorMode`.
- **Live `App` initializer drift.** Placeholders in the `App = { ... }` block must stay in sync with `Settings.APP_SCHEMA[i].def`. Resolution: the post-init live-`App` test (added in the test section) catches drift.
- **`markDirty` free variable in `Settings.applyApp` recipes.** `markDirty` is defined in `main.js` after `applyAppState`. JS resolves free variables at call time, so this works as long as `Settings.applyApp(...)` is only called after `markDirty` is defined — which is true at load/reset/init time. No code change needed; call out in the PR description.
- **`Settings` on the test sandbox global.** Confirmed: `stub-dom.js` sets `sandbox.window = sandbox`; the `settings.js` IIFE writes to `root` which is `window` in both the browser and the sandbox. `sandbox.Settings` is set before `gear.js` runs.
- **`def:LIMITS.<name>.def` referencing `LIMITS` at module-init.** Works because `LIMITS` is declared first in the same IIFE, before `APP_SCHEMA`. The file order is `LIMITS → APP_SCHEMA → helpers`.
